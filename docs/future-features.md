## 🌳 方案二：记忆树导航（Topic Tree）

### 核心思路

把扁平的事实库变成一棵**主题树**，Agent 可以主动「浏览」记忆，而不是只有 top-5 搜索。

```
根
├── 用户偏好
│   ├── 编辑器 (VS Code → Neovim)
│   ├── 语言 (Python, Rust)
│   └── 工作流 (TDD, CI/CD)
├── 项目
│   ├── Butterfly Dream (当前)
│   └── 旧项目X (归档)
└── 配置
│   ├── Hermes 配置
│   └── 服务器地址
```

**关键 API**：`fact_store(action='browse', path='用户偏好/编辑器')`

返回该节点的**全部**事实（而非 top-5），让复杂任务能看全上下文。

### 价值

- 解决 top-5 检索太浅的问题
- 层级浏览比关键词搜索更可靠（知道树结构就能导航，不需要猜关键词）
- 树结构可以被 LLM 理解并用于规划（"先看 用户偏好/编辑器，再看 项目/Butterfly Dream"）

### 论文来源

| 版本 | 论文 | 更新说明 |
|:----|:-----|:---------|
| 2024 原版 | **MemWalker** — 树形导航 + LLM 自主遍历 | 基础概念 |
| 2024 | **Memory Compass** — 层级记忆存储 | 补充参考 |
| **2025 升级** 🆕 | **MemWalker++** (ICLR 2025) — 树形导航 + **动态剪枝** + **预取机制** | **替代原版 MemWalker 作为主参考**。增加根据 Agent 当前计划预测并预加载相关节点的能力，减少检索延迟 |

### 工作量估算

~150 行

| 组件 | 说明 | 行数 |
|:----|:-----|:----|
| 树结构数据 | 从 facts 自动归类建立主题层级 | 50 |
| 自动分类逻辑 | 根据 category + tags + 关键词推断节点路径 | 40 |
| `browse` handler | tree 序列化 + 节点查询 | 30 |
| Tool schema | `fact_store` 新增 `browse` action | 20 |
| 测试 | 单元 + e2e | 30+ |

### 依赖

- 已有的 `category` 字段（`user_pref` / `project` / `tool` / `general`）
- 已有的 `tags` 字段
- 需要新增「主题路径」索引（或动态生成）

### 风险

- 动态分类可能不稳定（同一事实两次分类结果不同）
- 深树结构序列化 token 消耗大
- 用户自定义路径 vs 自动推断路径的冲突处理

## 🔄 方案三：主动记忆提醒（Proactive Recall）

### 核心思路

当前 prefetch 只在**用户发消息时**用最新一条消息搜 top-5，太被动。改为**整个对话上下文**决定要提醒什么。

**触发时机**（不仅 `on_pre_compress`）：

| 时机 | 触发动作 |
|:----|:---------|
| 话题切换 | 自动搜索新话题的旧相关事实，注入 prefetch |
| 检测到决策点 | 提醒之前类似决策的结果（好/坏） |
| 发现矛盾 | 主动 alert "之前你说过相反的" |

**目标**：让记忆从「被查的数据库」变成「主动参谋」。

### 价值

- 当前记忆是被动的：Agent 不搜 = 白存
- 主动提醒让记忆在**关键时刻**自然浮现
- 这个方向论文基本没人做好——Generative Agents 有一点但很弱

### 论文来源

| 版本 | 论文 | 更新说明 |
|:----|:-----|:---------|
| 2024 原版 | **MemGPT** — 事件驱动触发 | 基础概念 |
| 2024 | 认知科学中的「记忆提醒」机制 | 补充参考 |
| **2025 升级** 🆕 | **Memory3** (arXiv 2025) — **任务状态驱动的主动触发**，根据当前任务状态决定从哪层记忆回放 | **更优替代**：比规则式话题检测更智能，按 working/episodic/semantic 三层自动决策 |
| **2025 升级** 🆕 | **Event-Stream Memory** (ICML 2025) — 记忆带 **因果链**（时间戳+触因+情感），检索返回整条因果链 | **更优替代**：替代硬编码的话题切换/决策点检测——新消息匹配已有触因时自动触发因果回忆 |

> **结论**：2024 的 MemGPT + 规则方案已被 Memory3 + Event-Stream Memory 的超集思路替代。实现时直接参考 2025 方案，不再走规则检测。

### 合并后的推荐方案

结合 Memory3 的任务状态感知 + Event-Stream Memory 的因果链触发：

```
1. 每条事实存储时记录"触因"（什么导致了这条事实）
2. Agent 处理新消息时：
   a. Memory3 风格：判断当前处于什么任务阶段
   b. Event-Stream 风格：新消息中的实体/行为是否匹配已有事实的触因
3. 匹配 → 自动 inject 相关旧事实到 prefetch
```

### 工作量估算

~150 行（比原来多 30 行，因为因果链存储 + 匹配逻辑）

| 组件 | 说明 | 行数 |
|:----|:-----|:----|
| 触因提取 | 事实入库时同时提取触因（谁/什么导致了它） | 25 |
| 触因匹配 | 新消息与事实触因的 FTS5 匹配 | 25 |
| 任务状态跟踪 | Memory3 风格的任务阶段检测 | 30 |
| 主动注入 prefetch | 匹配时自动调用 `on_prefetch` | 20 |
| 熔断 | 避免每轮都触发浪费 token | 15 |
| 测试 | | 30+ |

### 依赖

- 已有的 contradiction 检测（`_is_contradictory`）
- 已有的 `tokenize()` / `jaccard_similarity`
- 已有的 async extraction 架构
- 需要新增触因（trigger/cause）字段到 facts schema

### 风险

- 触因提取依赖 LLM 额外字段输出，增加 token 消耗
- 任务状态检测可能漂移（Agent 自己判断不一定准）
- 频繁触发可能 token 浪费（熔断设计关键）
- 用户可能觉得"烦"——需要可配置开关

## 🧹 方案四：自适应遗忘（Adaptive Forgetting）

> 🆕 **来自 2025 新论文**— 之前未覆盖的方向

### 核心思路

当前事实库只增不减，长期会无限膨胀。设计一个**遗忘-巩固调度器**，根据访问频率、重要性、时效性自适应决定每条事实的命运：保留 / 压缩摘要 / 删除。

模拟人类记忆的**睡眠重放**机制：
- 低频 + 低重要 + 非持久 → 删除
- 中频 + 中等重要 → 压缩成一条摘要
- 高频 + 高重要 → 保留并提升权重

```
cron 每 N 小时跑一次：
  低优先级组 (trust<0.3, importance<3, is_persistent=0, 30天未更新)
    → 直接删除
  中优先级组 (trust 0.3-0.6, importance 3-6, 60天未访问)
    → LLM 压缩为一条摘要，删除原多条
  高优先级组 (importance≥7 或 is_persistent)
    → 不动
```

### 价值

- 库不会无限膨胀——当前已存几百条后搜索性能开始下降
- 自动清理噪音：那些"用户今天说喜欢 X"但再没提过的垃圾事实
- 压缩保留信息密度：多条相似事实→一条精准摘要

### 论文来源

| 论文 | 核心贡献 |
|:----|:---------|
| **Forgetting to Learn** (ACL 2025) — Patel, Gupta, Yang | 遗忘-巩固调度器 + **睡眠重放**（sleep replay），根据访问频率+重要性+时效性自适应决策 |
| **MemoryBank** (2024) — 衰减式遗忘 | 补充参考：按检索强度衰减，低到阈值删除 |

### 工作量估算

~120 行

| 组件 | 说明 | 行数 |
|:----|:-----|:----|
| 遗忘调度器 | cron 任务：扫描 + 分组 + 决策执行 | 40 |
| 压缩合并 | LLM 调用把多条事实 summarise 成一条 | 25 |
| 安全保护 | 防止误删高重要/持久事实 | 15 |
| 配置项 | 保留阈值 + 频率 + 白名单 | 15 |
| 测试 | 单元 + 集成 | 25+ |

### 依赖

- 已有 `importance` / `trust_score` / `is_persistent` / `updated_at` 字段
- 已有 LLM extraction 接口（可复用 `_call_extraction_llm`）
- 已有 cron 调度机制（Hermes 的 cronjob 系统）

### 风险

- 误删重要信息——需要**预览模式**（dry_run）
- 压缩合并可能丢失细节——需要保留原文引用
- 用户可能不信任自动删除——默认关闭，手动启用

## 🧠 方案六：LLM 智能去重（Smart Dedup）

> 🆕 **来自 MemOS 插件**（记忆张量 MemTensor，2026）— 同为 Hermes 生态的记忆插件

### 核心思路

当前去重是规则式的（`dedup_threshold` 余弦相似度 > 阈值就跳过）。改为让 LLM 判断新内容与已有记忆的关系：**完全重复 / 信息更新 / 全新内容**，分别采取不同策略。

```
用户先说："我在减肥，每天1800大卡"
用户后说："放弃减肥了，恢复正常饮食"

当前做法（规则去重）→ 两条都存，搜索时都返回，信噪比差
智能去重（LLM判断）→ 识别出第二条是对第一条的更新，合并为一条，记录演化历史
```

### 三种处理策略

| LLM 判断 | 策略 | 示例 |
|---------|------|------|
| 完全重复 | 跳过不写入 | 同一信息两次提到 |
| 信息更新 | 合并旧+新，标记演化关系 | "在减肥" → "放弃减肥" |
| 全新内容 | 正常写入 | 从未提过的信息 |

### 价值

- **记忆库保持干净**：不堆积重复/过时信息，信噪比持续保持高位
- **与演化链（方案五）天然配合**：智能去重的"信息更新"判断可以直接触发演化链的 `supersedes` 链接
- **检索质量提升**：去重后的记忆库更小更精准，搜索结果更相关

### 来源

| 来源 | 说明 |
|:----|:-----|
| **MemOS 插件**（记忆张量 MemTensor，2026） | Hermes 本地记忆插件，GitHub 8400+ Star |
| 核心理念 | "记忆不是存得多就好"，去重+合并让记忆库保持干净 |
| 实现方式 | 语义分片→LLM摘要→向量化→LLM智能去重 |

### 与现有方案的关系

| 现有功能 | 智能去重增强 |
|---------|-----------|
| `dedup_threshold` 规则去重 | 替换为 LLM 判断（可保留规则作为快速通道） |
| `contradict` 矛盾检测 | 互补：去重处理"同一事实的不同表述"，矛盾检测处理"互相冲突的事实" |
| 演化链（方案五） | 配合：智能去重的"更新"判断 → 自动建立演化链链接 |
| 自适应遗忘（方案四） | 配合：去重减少新增噪音，遗忘清理历史噪音 |

### 工作量估算

~100 行

| 组件 | 说明 | 行数 |
|:----|:-----|:----|
| LLM 去重判断 | 新事实入库前，搜索相似旧事实，LLM 判断关系 | 35 |
| 合并逻辑 | "更新"时合并内容 + 建立演化链链接 | 25 |
| 快速通道 | 高相似度直接跳过，不调 LLM（省 token） | 15 |
| 配置项 | 开关 + 阈值 + 合并策略 | 10 |
| 测试 | 单元 + e2e | 15+ |

### 依赖

- 已有的 `dedup_threshold` 和 `jaccard_similarity`
- 已有的 `_call_extraction_llm` 接口（复用）
- 演化链（方案五）的 `supersedes` 字段

### 风险

- 每条新事实都调 LLM 做去重判断，增加 token 消耗（可用快速通道缓解）
- LLM 判断可能误判（把不同事实判为重复）
- 需要搜索已有相似事实，增加写入延迟

## 📊 参考实现：MemOS 插件（记忆张量 MemTensor）

> 来源：逛逛 GitHub 公众号（2026），Hermes Agent 的本地记忆插件
> 开源地址：github.com/MemTensor/MemOS/tree/main/apps/memos-local-plugin

### 产品概况

MemOS 插件是记忆张量 MemTensor 团队为 Hermes Agent 开发的本地记忆插件，与 Butterfly Dream 同属 Hermes 记忆生态。MemOS 主仓库 GitHub 8400+ Star。

### 核心功能

| 功能 | MemOS | Butterfly Dream | 分析 |
|:----|:------|:----------------|:-----|
| 写入处理 | 语义分片→LLM摘要→向量化→智能去重 | LLM提取→存SQLite | MemOS 多了向量化 |
| **智能去重** | **LLM判断重复/更新/新，合并旧记录** | dedup_threshold 规则 | **MemOS 最大差异化** |
| 检索引擎 | FTS + 向量语义 + 融合排序 + 时间衰减 | FTS5 + 三维检索 | 各有优势 |
| 预检索 | 每轮自动预检索注入上下文 | prefetch() | 持平 |
| 多Agent协同 | 同机共享+跨机Hub-Client | 无 | 我们缺失 |
| 管理面板 | Web UI (7页面) | CLI | MemOS 体验更好 |
| 部署 | 需Bridge守护进程 | 纯Python包 | 我们更轻量 |

### MemOS 的优势

1. **LLM 智能去重**：不是简单的文本比对，而是让 LLM 判断关系（重复/更新/全新），然后合并
2. **混合检索**：FTS + 向量语义，关键词对不上也能搜到
3. **三级模型配置**：embedding/摘要/技能生成可独立配置

### 与 Butterfly Dream 的差异

1. **token 消耗更大**：需要 embedding + 摘要 + 去重多次 LLM 调用
2. **没有信任评分**：我们有 trust_score，MemOS 没有
3. **没有矛盾检测**：我们有 contradict，MemOS 只做去重
4. **没有演化链**：我们即将做方案五，MemOS 没有
5. **部署更复杂**：需要守护进程，我们是纯 Python 包

### 改进启示

| 优先级 | 改进项 | 来源 |
|:------|:------|:-----|
| P0 | LLM 智能去重 | MemOS |
| P0 | 演化链 | Hy-Memory |
| P1 | 向量语义检索通道 | MemOS |
| P1 | 时间衰减排序 | MemOS |
| P2 | Web 管理面板 | MemOS |

## 🖥️ 方案七：Web 管理面板（Memory Dashboard）

> 🆕 **来自 MemOS 插件**（记忆张量 MemTensor，2026）— 同为 Hermes 生态的记忆插件

### 核心思路

提供一个本地 Web UI 来可视化管理记忆库，替代纯 CLI / fact_store 命令行操作。默认地址 `http://127.0.0.1:18901`，密码保护，仅本地访问。

### 功能模块

| 页面 | 功能 | 价值 |
|:----|:-----|:-----|
| 记忆浏览 | 按分类/时间/重要性浏览所有事实 | 直观查看记忆库全貌，不用 list 一个个翻 |
| 记忆搜索 | 关键词 + 分类筛选 | 快速定位特定记忆，比 fact_store search 更友好 |
| 编辑/删除 | 在线修改事实内容、重要性、分类 | 方便清理和修正错误记忆 |
| 演化链可视化 | 展示事实之间的 supersedes 链接 | 方案五实现后，直观看到记忆演化轨迹 |
| 统计面板 | 事实总数、分类分布、存储趋势 | 了解记忆库健康状况 |
| 导入/导出 | JSON/CSV 格式备份和恢复 | 数据迁移和备份 |
| 配置管理 | 在线调整重要性阈值、去重策略等 | 不用改 config.yaml 就能调参 |

### 价值

- **降低使用门槛**：新用户不需要学 fact_store 命令就能管理记忆
- **可视化调试**：排查记忆问题（为什么搜不到？为什么重复？）时直接看面板
- **记忆清理**：定期通过面板清理过时/错误记忆，保持库健康
- **展示友好**：演示 Butterfly Dream 功能时有直观的 UI

### 实现方案

纯前端 SPA（HTML/CSS/JS），不需要后端服务——直接调用 Butterfly Dream 的 Python API：

```
方案 A（轻量）：单 HTML 文件，内嵌 JS 直接调 SQLite
  - 需要一个 tiny Flask/FastAPI 服务暴露 API
  - 优点：最简单，~200 行

方案 B（完整）：React/Vue SPA + REST API 服务
  - 优点：交互体验好，可扩展
  - 缺点：复杂度高，需要 Node.js 构建

推荐方案 A，先跑起来再说
```

### 工作量估算

~200 行（方案 A）

| 组件 | 说明 | 行数 |
|:----|:-----|:----|
| API 服务 | Flask/FastAPI 轻量 HTTP 服务 | 50 |
| 记忆 CRUD | 列表/搜索/编辑/删除 API | 40 |
| 统计接口 | 分类分布/趋势数据 | 20 |
| 前端 HTML | 单页面，内嵌 JS/CSS | 80 |
| 启动/配置 | 端口/密码/启动方式 | 10 |

### 依赖

- 已有的 `MemoryStore` 数据库接口
- 新增 Flask 或 FastAPI 依赖（可选，也可用 http.server 内置模块）

### 风险

- 安全：必须限制为 localhost 访问 + 密码保护
- 依赖：增加一个可选的 web 框架依赖
- 维护：UI 需要随功能迭代更新

| 7 | **Memory Benchmark** (arXiv 2025) — 统一评测：检索精度+遗忘曲线+跨 session 推理+记忆污染 | 标准化测试集，验收改进效果 | 不是功能特性，而是验证工具——做改进时可用它检验 |

## 🧬 方案五：演化链（Evolution Chain）

> 🆕 **来自腾讯 Hy-Memory** — 为 OpenClaw 长期协作 Agent 设计的记忆插件

### 核心思路

当同一主题的事实发生多次更新时（如用户偏好变化、技术选型迭代），用 `supersedes` 指针把相关记忆串成链。搜索命中链上任意节点时自动展开整条链，让 Agent 看到完整的演化轨迹而非孤立结论。

```
用户问："我下个月想加一种新训练方式"

覆盖派（只记最新）→ 推荐 CrossFit（不知道用户 HIIT 伤过膝盖）
堆积派（全部保留）→ 搜索按相似度召回，旧事实语义距离太远召不回
演化链（链式追踪）→ 命中链头 D，自动展开 A→B→C→D 完整轨迹
  D: 混合训练稳定（链头）
  ↓ supersedes
  C: 纯力量丢心肺
  ↓ supersedes
  B: HIIT 伤膝盖
  ↓ supersedes
  A: 跑步起步
→ 推荐游泳/骑行等低冲击有氧，避开 CrossFit/HIIT
```

### 价值

- **矛盾检测升级**：当前 `_is_contradictory` 是独立检测，发现矛盾后两条事实各存各的。演化链把它们串成因果关系，查询时自动带上完整上下文
- **时序场景质的飞跃**：当前 timeline 查询需要手动设定 entity，演化链让同一主题的多次更新自动形成时间线
- **检索质量提升**：命中链头就能获得完整演化路径，不需要同时搜到所有历史事实

### 与现有方案的关系

| 现有功能 | 演化链增强 |
|---------|----------|
| `contradict` 检测 | 矛盾事实自动建立 supersedes 关系 |
| `timeline` 查询 | 链式展开替代手动 entity 关联 |
| 记忆编辑（update） | 更新时自动链接到被替代的旧事实 |
| 记忆树导航（方案二） | 树提供空间导航，演化链提供时间导航 |

### 来源

| 来源 | 说明 |
|:----|:-----|
| **Hy-Memory**（腾讯，2026） | 为 OpenClaw 设计，6层记忆 + System1/System2 双系统 + 演化链 |
| LongMemEval 评测 85.2 分 | 偏好 +21pp，时序推理 +10pp，知识更新 +21pp |
| PersonaMem 评测 | 6000+ 条消息 / 589 道题，超过所有同类产品 |
| 性能数据 | 记忆条数 mem0 的 1/3，单条信息密度 3-4x，写入速度 8x Graphiti |

### 实现要点

```
facts 表新增字段：
  superseded_by  INTEGER  -- 指向替代它的新事实（链头方向）
  supersedes      INTEGER  -- 指向它替代的旧事实（链尾方向）

写入逻辑（add_fact / update）：
  1. 新事实入库时，检查是否有同 entity + 同主题的旧事实
  2. 若有：旧事实设 superseded_by = 新事实 ID，新事实设 supersedes = 旧事实 ID
  3. 形成链：D.supersedes=C, C.supersedes=B, B.supersedes=A

检索逻辑（search）：
  1. 搜索命中某个事实 F
  2. 从 F 沿 supersedes 指针回溯整条链（最多 10 节）
  3. 链头排在最前，链身按时间倒序排列
  4. 返回链头 + 链身作为完整结果
```

### 工作量估算

~120 行

| 组件 | 说明 | 行数 |
|:----|:-----|:----|
| schema 变更 | facts 表新增 superseded_by / supersedes 字段 | 15 |
| 写入链构建 | add_fact 时自动检测同主题旧事实并建立链接 | 30 |
| 检索链展开 | search 返回结果时沿指针回溯展开 | 25 |
| 矛盾自动链接 | contradict 检测后自动建立 supersedes 关系 | 20 |
| 评测场景 | 新增演化链评测用例 | 15+ |
| 测试 | 单元 + e2e | 15+ |

### 依赖

- 已有的 `contradict` 检测
- 已有的 entity 关联（`_link_entities`）
- 已有的 timeline 查询
- SQLite ALTER TABLE 新增字段

### 风险

- 主题匹配依赖 LLM 或关键词，可能误链接不相关事实
- 长链（>10 节）展开消耗 token，需要限制链长度
- 与自适应遗忘（方案四）交互：删除链中间节点会断链
